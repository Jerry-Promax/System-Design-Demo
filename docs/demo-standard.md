# Demo 交付规范

一个场景只有同时满足“能讲清、能运行、能验证、能讨论取舍”才算完成。

## 目录约定

```text
demos/<scenario>/
├── README.md
├── pom.xml
└── src/
    ├── main/
    │   ├── java/...
    │   └── resources/application.yml
    └── test/java/...
```

模块名使用短横线英文，例如 `rate-limit`、`idempotency`、`cache-consistency`。题目编号只出现在索引和文档中，不进入模块名，避免后续调整顺序时大面积改路径。

## README 必须包含

1. **场景与追问**：这道题真正想考什么，常见追问有哪些。
2. **Demo 边界**：做了什么，故意不做什么。
3. **核心流程**：用一段文字或 Mermaid 图说明一次请求的路径。
4. **运行方式**：启动命令、依赖和端口。
5. **演示步骤**：可直接复制的请求，以及预期结果。
6. **验证方式**：测试命令和测试覆盖的关键行为。
7. **生产差距**：单机改多机、内存改持久化、一致性、观测、容量和安全。

## 代码约定

- Java 21，Spring Boot 3。
- 包名统一以 `com.sysdesign.<scenario>` 开头。
- 业务逻辑与 HTTP 适配层分开，核心算法应能脱离 Spring 单测。
- 时间、随机数、外部存储等不稳定因素通过构造参数注入。
- 允许内存实现，但要在类名或 README 中明确，例如 `InMemoryOrderRepository`。
- 若确实需要 Redis、数据库或消息队列，提供 `compose.yaml`，并说明不启动基础设施时哪些测试会跳过。
- 默认不得依赖公网服务或真实第三方密钥。

## 测试约定

至少覆盖以下三类中的两类：

- **正常路径**：核心机制按预期生效。
- **边界与竞态**：窗口边界、重复请求、并发扣减、超时和重试等。
- **失败与恢复**：下游不可用、消息重复、补偿成功等。

测试不应依赖真实等待。优先使用虚拟时钟、可控故障开关和确定性调度。

## 可观测性约定

Demo 至少应让读者看见关键结果，方式可以是：

- 返回解释性响应字段；
- 输出结构化日志；
- 暴露内存状态查询接口；
- 在测试断言中直接验证状态。

不要仅返回一个无法判断内部效果的 `success: true`。

## 完成检查表

- [ ] 题目和 Demo 边界写清楚。
- [ ] 一条命令可以启动。
- [ ] 一组请求可以触发核心行为。
- [ ] 至少一个自动化测试。
- [ ] 关键故障或竞态可复现。
- [ ] 生产化差距有明确说明。
- [ ] 根 README 和场景索引状态已更新。
